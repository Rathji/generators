🔌 ai-code-tool-integration

A Perchance plugin (rathji-plugin-template structure) that bridges a local dev workspace and a 3rd-party AI coding platform — secure sessions, context sync with token budgets, prompt dispatch, code-block parsing, gated file application, logs with rollback, and friendly API-error handling.

How it works

This plugin is one continuous pipeline. A session owns the connection to the AI platform; a workspace is any object mapping file paths to content (a plain file-table object works everywhere; in a capable browser it can also be a real directory handle). Everything that flows between the two — context, token budgets, prompts, parsed responses, applied changes — passes through twelve composable, individually-testable helpers:

  1. Connect. aiCode(...) — whatever you named the import — validates config and returns a session handle; authenticate() proves the credentials against the platform via a built-in probe, or your own transport function.
  2. Stay alive. An optional heartbeat re-verifies the session on a timer and reconnects with exponential backoff, so a stale connection never silently poisons a prompt.
  3. Handle keys. API keys live in a per-user browser store and are only assembled into an Authorization header at the last instant — source, logs, page output and JSON.stringify never contain them.
  4. Map the workspace. The index builds a structural tree (paths, sizes, mime types — never contents) with sane built-in ignore rules.
  5. Choose context. Injection selects files by exact path, glob or substring and formats their contents as tagged, size-capped blocks.
  6. Cap the window. The token budget counts what the prompt will really cost and refuses to overspend.
  7. Ask. The dispatcher sends context + prompt to the platform (SSE streaming, pluggable transport) and returns a normalized result.
  8. Understand the reply. The parser separates prose from code blocks, each tagged with language, path and line range.
  9. Plan the edit. Application computes each change's diff without writing a single byte.
  10. Get consent. The gate holds every change pending until a human approves; only then does the writer run.
  11. Audit & undo. The log records every prompt and applied change (persisted across reloads) and can roll the last N back byte-for-byte.
  12. Translate failures. The error bridge turns any status or error code into \{severity, userMessage, action\} and funnels every plugin error into one notify hook.

The design contract. Every helper returns a typed object — \{ok:true, ...\} on success, or \{ok:false, code, message, severity, userMessage, action\} on failure — and nothing ever throws. That same object is what renders inside a Perchance list (\[aiCode(myConfig)\] shows a readable status line) and what a script branches on (if (r.ok) ...). The modules compose in a fixed order but each is usable on its own: you can budget without indexing, parse without applying, or gate without a log.

The numbered module sections below are the reference; the demos run the real plugin functions on this page.

Module 1 — the connection protocol

The plugin's entry function returns a session handle. A session is created from an options node or plain object; calling authenticate() establishes the secure session:

  1. Required options are validated (baseUrl + apiKey; missing ones are named, never thrown).
  2. A session object is minted: unique id, timestamps, status lifecycle (unauthenticated → authenticating → connected | auth_failed | error), and a redacted key fingerprint for display.
  3. The raw key is stored non-enumerably on the session and is used only to build the Authorization header on demand — it never appears in JSON.stringify(session), console output, or the session's readable form.
  4. authenticate() runs a handshake: by default it probes GET baseUrl/probePath with the auth header (2xx → connected; 401/403 → auth_failed; timeouts, network failures and HTTP errors are classified). You can instead supply your own transport function — the demo below uses one to simulate a remote platform.

Module 2 — health monitoring (heartbeat)

Any session can run a heartbeat — periodic checks that the session is still alive, with automatic reconnection when it isn't:

  1. session.startHeartbeat(opts) starts the monitor (also automatic via the heartbeatEnabled option). session.stopHeartbeat() stops it; session.heartbeatStatus() reads the state.
  2. Each check re-runs the session handshake. The heartbeat is single-flight: overlapping checks are skipped, and exactly one next check is ever scheduled, so a failure can never fan out into duplicate reconnection sequences.
  3. A failed check increments a consecutive-failure counter and flips the monitor to reconnecting; the next attempt is scheduled with exponential backoff (start at heartbeatBackoffMs, doubling up to heartbeatBackoffMaxMs).
  4. Recovery resets the counter, logs reconnect-ok and returns to the normal heartbeatIntervalMs cadence. Rejected credentials (auth_failed) are treated as terminal: the monitor goes down and halts, since retrying would not help.
  5. Every transition is recorded in controller.history — a status event log with events start / check-ok / check-fail / reconnect-ok / reconnect-fail / auth-fail / stop plus timestamps, failure counts and next-retry delays. An optional onEvent callback receives each entry live.

Module 3 — credential management (secure local key store)

API keys should never sit in generator source. The plugin ships a per-user credential store that lives entirely in the browser:

  1. aiCodeToolIntegrationCredentials(opts) returns a store handle for one named profile (default "default"), so keys for several platforms can be kept apart.
  2. await store.ingest(key) saves a key once, from user input — never from source. Storage is per-user and local: kv-plugin (IndexedDB) on the page's own origin, with localStorage as a fallback. Nothing is ever uploaded.
  3. await store.get() returns a display-safe shape: a redaction that masks everything but the last 4 characters, plus a fingerprint. The raw key never appears in it, in JSON.stringify, in describe(), or in console output.
  4. await store.clear() wipes the stored key. Sessions use the store via the credential option — authenticate() pulls the raw key out at the last moment to build the auth header, so the key never exists in the calling code.

Honest note: the key is stored unencrypted inside the browser's own storage partition (like any local credential store) — but the generator source, page output and logs contain only placeholders, masks and fingerprints.

Module 4 — file system indexing (structural context map)

aiCodeToolIntegrationIndexTree(source, opts) walks a workspace and returns its root directory node — a normalized, content-free structural map that Module 5 will consume when it decides which files deserve prompt context:

  1. Two ways to hand it a workspace. An injected file table — a plain object mapping workspace-relative paths to content or metadata — works in any environment (including this docs page, which cannot enumerate local folders without permission). A File System Access directory handle (real or duck-typed: kind directory plus a values() iterator over name/kind entries) is walked depth-first and asynchronously where the browser supports it.
  2. File-table values. A string, Uint8Array, ArrayBuffer, Blob or DataView of bytes; a number as a byte-count placeholder; null for an empty text file; or a metadata object with size, type, bytes or content, and dir. Paths ending in a slash (or carrying a dir: true value) declare directories — the way to express empty ones. Backslash separators are normalized; empty paths, ".." segments and file-versus-directory conflicts are rejected loudly as ok:false errors, never thrown.
  3. Ignore rules. Built-in defaults skip node_modules, .git and similar noise; opts.ignore adds patterns — exact names, *-globs, or slash-paths matched against the workspace-relative path (e.g. the pattern docs/generated/** ignores that whole subtree); opts.ignoreDefaults: false clears the built-ins. Binary files are excluded by default (known binary extensions, binary mime types, or NUL bytes in the first 1 KB when content is available) unless opts.includeBinaries is true — their bytes would only waste context tokens.
  4. Node shape. Every node carries kind, name, path, size, type and children; files keep children: null; directories are listed first, then files, each alphabetically, and a directory's size aggregates the file bytes beneath it. Real (even empty) directories from a handle are kept; auto-created empty ones from a table are pruned. aiCodeToolIntegrationTreeStats(node) reduces the whole tree to dirCount, fileCount and totalBytes — exactly the inputs Module 6's token budget needs.

Module 5 — targeted context injection (contents into the prompt)

aiCodeToolIntegrationInject(source, query, opts) is the content counterpart to Module 4's structural map: it reads the files the index flagged as relevant and formats their contents as tagged context blocks for the prompt:

  1. Selection. query is an exact path, a glob pattern, or a case-insensitive path substring — or an array of any of these. Globs with no slash match the file name at any depth (*.js → every JS file in the workspace); slash globs match from the root (src/** → the whole subtree; **/*.test.js → tests anywhere). An object query with a path field plus an optional maxBytes field adds a per-file cap. Files matched by several queries are injected once (first match wins).
  2. Reading. The same source IndexTree accepts (a file table or a directory handle) is reused, so the same ignore rules apply — node_modules and friends never leak contents into a prompt. Binary files are skipped and counted. Table values are decoded (string / typed-array / ArrayBuffer / Blob); directory-handle files are read through getFile(), with read failures counted, never thrown.
  3. Block format. Each file becomes a fence-delimited block with an unambiguous, machine-parseable boundary — ----- FILE: path ----- … ----- END FILE: path ----- — plus a type and byte-size line. Oversized files are truncated to opts.maxBytes (default 8000) with a visible marker; empty files and byte-count placeholders get explicit markers too.
  4. Window control. opts.maxFiles limits how many files are injected (default 25); opts.totalBytes caps the whole window (injection stops before exceeding it); opts.context appends the new blocks to an existing context window. The result carries the built context string, the structured blocks, and a stats summary — exactly what Module 6's token budget will reason over and Module 7's dispatcher will send.

Module 6 — token budget tracking

aiCodeToolIntegrationTokenEstimate(text) and aiCodeToolIntegrationBudget(opts) put a hard, honest cap on how much context flows toward the model:

  1. Estimation. estimate(text) counts UTF-8 bytes and divides by 4 (rounded up) — a conservative stand-in for token count; it is monotonic (appending text never lowers the estimate).
  2. The budget controller. budget = aiCodeToolIntegrationBudget(\{limit, overhead\}) starts at used = overhead (default 0) and always reports \{ok, kind, limit, overhead, used, remaining, addCount\} with the invariant used + remaining === limit. budget.add(text) reserves space for a string, refusing with a typed budget_exceeded when the window is full (or truncating the text to fit when \{truncate:true\}); budget.charge(tokens) counts explicit token values; budget.reset() zeroes back to the overhead. Nothing ever throws.
Add text to the budget — it reports used/remaining and refuses (typed) once the window is full.

Module 7 — prompt dispatcher

aiCodeToolIntegrationDispatch(session, payload, opts) is the bridge's outbound half — it packages context + prompt + optional system prompt into a chat/completions request, sends it, and returns a normalized result:

  1. Payload & defaults. payload = \{prompt, context?, system?, model?\}. context (e.g. the Module 5 injection window) is concatenated above the prompt; model falls back to the session's. A missing prompt is a typed missing_prompt error.
  2. Session-first. The session must be connected; if not, dispatch re-authenticates first (and fails with a typed session_down/auth_failed if it still isn't).
  3. Transport. The default transport POSTs \{model, messages\} to baseUrl/chat/completions and SSE-streams chunk-by-chunk when the response streams (onChunk); a custom transport function replaces it entirely (the demo below stubs one — no real request leaves the page).
  4. Result. \{ok, content, raw, model, usage, streamed, estimatedTokens, tookMs, sent\}. Errors — 401/403 → auth_failed, non-2xx → http_error with status, timeouts and network failures classified — all come back as bridge-ready error objects (Module 12), never thrown. An optional budget (Module 6) is checked and charged before sending; an optional log (Module 11) records the prompt.
Dispatches through a local stub transport so you can inspect the exact request/result shape.

Module 8 — response parser

aiCodeToolIntegrationParse(text) splits an AI response into conversational prose and machine-parseable code blocks — the counterpart to Module 5's injection format and the input to Module 9's application:

  1. Fences. Blocks are delimited by triple backticks. An opening fence's hint is parsed language-first, then an optional path (```javascript src/foo.js). Prose outside fences is collected as the conversation (trimmed, code-free).
  2. Block shape. Each block carries \{lang, path?, code, startLine, endLine\} (1-based, monotonic) plus unclosed when a fence never closes — the parser recovers to the end of the response and flags it rather than dropping the code.
  3. Result. \{ok, conversation, blocks (array), stats\{blocks, fences, unclosed\}\}. Non-string input → typed invalid_parse_input, never thrown.
Parses the response into prose + blocks with language, path, line ranges and code.

Module 9 — local file application

aiCodeToolIntegrationApply(source, blocks, opts) takes parsed blocks and computes their effect on a workspace — without writing anything unless told to. The "workspace" is a portable writable file-table object (path → content), the sandbox-safe stand-in for a local directory:

  1. Modes. Each block is \{path, code, op?\}: overwrite (default) replaces the file (or creates it with \{create:true\}); insert merges without touching surrounding content — after line \{line: N\} (0 prepends, past-end appends) or around a \{marker, position:"before"|"after"\} on its own line (missing marker → insert_anchor_missing).
  2. Safety. Binary files and directory targets are refused loudly (target_is_binary/target_is_directory); unknown paths fail with target_missing unless create:true. Every block becomes a change record \{id, path, op, oldBytes, newBytes, existed, diff\} — the line diff (LCS, whole-file fallback for huge files) is computed so a reviewer sees exactly what will change.
  3. Routing. With a Module-10 gate, records queue as gated and nothing is written until approved. Without a gate they are prepared dry-runs unless \{apply:true\} explicitly writes (or you pass a custom commit).

Module 10 — change validation gate

aiCodeToolIntegrationGate(opts) is the approval chokepoint between the AI and the workspace — nothing reaches the writer until a human approves:

  1. Queue. gate.enqueue(change) validates the record, computes its diff, and holds it as pending. The writer is never called by an unapproved change.
  2. Decisions. await gate.approve(ref) / gate.reject(ref) take the record or its id; approveAll() / rejectAll() clear the queue. Approval runs the commit function (via opts.commit or gate.setCommit(fn)); a throwing writer becomes a typed commit_failed, never an exception. With no commit set, approval is recorded with committed:false and a clear message.
  3. Audit. Every event (enqueue/approved/rejected/commit_failed) lands in gate.history (bounded at 200) and fires opts.onEvent. Invalid records, a full queue (maxPending) and unknown references are all typed errors. Give the gate a log (Module 11) and approvals auto-record change + approval entries.
End-to-end: parse a response → stage through the gate → review the diff → approve or reject → workspace updates. A log is wired in, so approvals record.

Module 11 — execution log (with rollback)

aiCodeToolIntegrationLog(opts) keeps an append-only audit trail and can undo the last N applied changes:

  1. Entries. Append-only \{ts, kind, payload\} where kind is prompt | change | approval | rollback. Dispatch with \{log\} records prompts; the gate with \{log\} records applied changes + approvals. Bounded (default 500 entries, oldest trimmed).
  2. Persistence. Entries persist across reloads via kv-plugin (folder named by opts.storage, default aiCodeToolIntegrationLog); a fresh log.load() restores them. If storage is unavailable the log still works in-memory — never throws.
  3. Rollback. await log.rollback(n) walks back through the last n un-reverted applied changes, writing each one's previous bytes back (in reverse application order) through the commit function or a source file-table; a change that created the file deletes it. Reverted changes are marked rolledBackAt (audit keeps everything), and the rollback itself is logged.

Module 12 — error handling bridge

aiCodeToolIntegrationErrors(opts) turns 3rd-party API failures into actionable notifications — the final safety layer of the whole pipeline:

  1. Mapper. Every status/code maps to \{severity, userMessage, action\} — 429 → warn "rate-limiting" with a backoff hint (retryAfterSeconds), 401/403 → "credentials rejected", 5xx → "retry shortly", timeout → warn retry, network → "couldn't reach", unknown → generic fallback.
  2. Central notify hook. errors.setNotify(fn) wires a UI sink. No-arg aiCodeToolIntegrationErrors() returns the shared default controller that every error the plugin constructs already funnels through (the base error constructor auto-attaches severity/userMessage/action and auto-captures) — so one setNotify catches everything. With opts you get a private controller for local capture().
  3. Capture & history. errors.capture(anything) accepts plugin error objects, plain \{status, code, message\}, or raw exceptions (→ unexpected_error with its safe message), records into a bounded history (consecutive identical errors dedupe with a count), and fires notify. Nothing ever throws.
Feed fixtures through the shared errors controller — the notify hook renders each one as an actionable banner.
Each fixture is mapped to severity + userMessage + action (+ retryAfter for 429).

End to end — the whole loop

Every module is composable, and the full pipeline is a single loop: connect (1) → heartbeat (2) keeps it alive → credential store (3) feeds the key → index (4) maps the workspace → inject (5) fills the context window → budget (6) caps it → dispatch (7) sends the prompt → parse (8) pulls code blocks out of the response → apply (9) computes their effect → gate (10) requires your approval before anything is written → log (11) records and can roll back → and errors (12) turn any failure into an actionable message. Here it is wired as one annotated function:

  1. Prepare. A session (1) is created from baseUrl + a credential; credential: true pulls the key from the store (3), so none ever appears in source. A heartbeat (2) is optional but keeps the session honest.
  2. Build context. The workspace is indexed (4) and the files the prompt cares about are injected (5) as tagged blocks; the budget (6) reserves exactly enough tokens and refuses if the window is full.
  3. Round trip. The dispatcher (7) sends context + prompt and streams the reply; the parser (8) splits prose from code blocks.
  4. Consent. Application (9) computes diffs and queues them in the gate (10) as pending — nothing is written until approveAll() runs the writer. The log (11) records changes as they land.
  5. Recovery. Any 429/500/timeout/network failure is mapped by the error bridge (12) to a severity, a human message and a suggested action — and if a change turned out wrong, log.rollback(n) reverts the last n byte-for-byte.
