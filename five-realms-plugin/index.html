⚔ five-realms-plugin

An MTG-compatible rules engine — a 28-card fixture database, zones, turn structure, priority, mana, seeded shuffling, an action reducer, a 52-asset inline-SVG card renderer. One 13-op $output, none of them throw. Stack resolution with targeting, combat damage, the full state-based-actions loop, a layered continuous-effects store, a keyword-ability library, and replacement effects are all implemented.

What this is

A Perchance plugin is just a normal generator written to be reused. The one special thing is the $output function at the bottom of main.pjs — when another generator imports this one, the name on the left of the import line becomes that function. The lists, data and helpers below it are all ordinary Perchance code.

five-realms-plugin is an MTG-compatible card-game engine: a fixture card database, the full game-state model (zones, turn structure, priority, mana), a seeded deterministic PRNG, a single never-mutating applyAction reducer, and an inline-SVG card renderer with 52 embedded assets. Stack resolution with targeting, combat damage, the full state-based-actions loop, layers and continuous effects, a keyword-ability library, and replacement effects are all implemented.

This page doubles as the plugin's docs and a live test harness — every claim below is exercised by the demo at the bottom.

API — 13 ops

Every op is reached through the same multi-parameter $output(op, a, b, c, d, e). None of them throw: an unresolvable id, a malformed state, or an unrecognised op all come back as a readable placeholder string (or an empty array, for the ops that promise one), never an exception.

Action objects passed to fr("act", ...) are plain \{ type, ... \} records. Phase 1 recognises eight types: concede, passPriority, playLand, castSpell, activateAbility, tapPermanent, declareAttackers, declareBlockers. An unrecognised type is recorded on the returned state's lastActionError rather than thrown.

Worked calls

Card record schema

All fixture cards share this shape. manaCost, power/toughness, and producesMana are omitted entirely (not set to ""/null) when they don't apply — lands have no manaCost, and non-creatures have no power/toughness.

The five realms and five tier names

Five realms, each mapped to a mana letter, a glyph asset, and a cost-symbol asset:

Five tier names, of which four are rarity steps ascending Marked → Vaulted → Sovereign → Ascendant: Field is not one of them — it denotes the basic-land card class and carries no gem. Rarity is drawn as a separate gem overlay rather than as a frame variant, so a card's frame is chosen by realm or card class and its gem by rarity, independently. fr("gem", cardIdOrRarity) and every fr("render", ...) call's gemSvg/gemSmallSvg fields wire this in; fr("gem", "Field") and any unrecognised rarity both come back as a placeholder string rather than a gem.

52 assets, in six families

The embedded payload grew from its original 12 assets (5 glyphs, 6 fronts, 1 back) to 52. fr("render", ...) picks a card's front itself — you never choose the asset id by hand:

The precedence fr("render", ...) uses to pick a front, highest first:

Only the original 6 realm/colourless fronts publish a palette — front-land/front-gold/front-artifact/front-basicland-* do not, so r.palette is undefined for a card rendered on one of those and this page's demo falls back to a neutral ink colour rather than crashing.

Multicolour rendering was previously deferred. The card-model spec's section 3 originally called multicolour glyph rendering out of scope, since no phase-1 fixture card needed it. This bucket un-defers that: any card whose colors (or, absent that, colorIdentity) has 2+ entries now resolves to front-gold rather than being left unhandled.

Live demo

Rendered by the plugin itself on this page: fr("render", id) hands back bare frontSvg/glyphSvg/gemSvg/gemSmallSvg plus a rects/palette/costSymbols envelope, and the script lays the name, mana-cost symbols, type line, gem, rules text, and P/T over those rects as absolutely-positioned HTML — exactly the composition a consuming generator is expected to do. No font is required for the SVG itself; the overlay text uses the browser's own serif stack.

How a multi-symbol cost fits a front that draws one circle. The front's costArea is a single 34×34 circle, but an MTG-compatible manaCost runs to several symbols — "\{1\}\{R\}\{R\}" is already in the fixtures. fr("cost", manaCost) returns an ordered array, one entry per symbol, so the consumer lays them out itself: the last symbol sits in the circle and the rest flow leftward along the name bar, with the card name truncated before it would collide. The circle deliberately no longer carries the realm glyph — the cost symbols already name the realm, so painting it there stated the same thing twice.

What phase 1 does not do

The engine covers the state model, zones, turn structure, priority, mana, a seeded PRNG, and the applyAction reducer. Deliberately deferred to a later phase, with a clean seam left for each:

  • Done in phase 2 (stack resolution + combat damage). frStackResolveTop now actually resolves each fixture spell and ability: permanents enter and fire their enter triggers (Sunward Sentinel's 2 life, Nautilus Seer's draw-and-discard), auras attach and grant their buff, Verdant Surge gives +3/+3, Withering Grasp destroys, and Faceted Ember Core's \{3\},\{T\},sacrifice deals 3 damage to any target. Spells/abilities take and validate targets, combat assigns damage (blocked vs. unblocked) at the combat-damage step, and lethal-damage death and life-loss are handled as state-based actions.
  • Done (state-based actions as a full loop). Beyond phase-2's lethal damage / life-loss / aura-about-to-fall-off, frCheckStateBasedActions now runs a real 704-style loop (re-runs until a pass changes nothing) and is checked before each priority grant.
  • Done (layer system + continuous effects). A timestamp-ordered (rule 613.7) continuous-effect store (state.effects) with a rule-7 P/T layer and EOT expiry; aura/vulnerability and Verdant Surge buffs flow through it.
  • Done (replacement effects). A rule-614 replacement layer (frReplacementEffects) is exposed on a permanent's card.replacement; the fixtures use a prevention replacement — Sunfire Aegis prevents all combat damage that would be dealt to its controller, including excess trample spill.
  • More keywords (each mechanically backed: hexproof and ward protect permanents from opponent targeting — hexproof blocks it outright, ward counters it; indestructible ignores lethal damage and destroy effects; skulk limits to equal-or-lower-power blockers) and further nontrivial abilities (lifelink, haste, vigilance, reach, menace).
  • fr("legalActions", ...) now enumerates planar-legal moves: a tapPermanent for every untapped permanent (tap a source first, then spend it), mana abilities and castable spells it can actually pay, and full attacker/blocker declarations — blocker matching honours flying/reach and menace. On very large boards the subset enumeration caps and reports solo attackers instead of every combination.

Notes

  • 52 assets, one inline payload — zero external requests, reconstructed byte-identical to the source SVGs.
  • Bare SVG, not composed HTML. fr("render", ...) never bakes text into the SVG it returns — layout, fonts, and escaping are entirely the consumer's job. This page's demo script is one worked example of that job, not the only correct way to do it.
  • Never throws. Any op, with any input — including null, an unknown id, or a deeply nested object — returns a placeholder value instead of raising an exception.
  • This is phase 1 of a game, not a finished game client: legality is best-effort (see above), and there is no matchmaking, persistence, or UI here beyond this demo page.
