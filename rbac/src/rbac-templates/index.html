🛡️ rbac — role-based access control for Perchance apps

Define roles and permissions, assign them to users, and enforce them in the UI and authoritatively on the server. Wildcard permissions, deny-overrides, role inheritance, durable server state and an admin API — all in one import. Built following the structure of Rathji's plugins.

What this is

A Perchance plugin is just a normal generator written to be reused — the special part is the $output function at the bottom of main.pjs, which is what an importing generator receives. This plugin ships two security layers:

  • Pure engine (client-side, offline) — rbac("engine") gives you roles, wildcard permissions, deny-overrides, inheritance and bans for UI gating and single-player apps.
  • Authoritative server (server-plugin) — rbac("serverScript") returns a paste-in server script with durable user/role state, admin authentication and admin RPCs. This is the real security layer — client-side checks are cosmetic.

This page doubles as the plugin's docs and a live test harness — the demo at the bottom exercises every claim below against a real server-plugin socket.

Resource ownership & sharing

Plain permissions are global — they apply to every document. To let a user manage their own documents, or edit documents shared with them, hand them scoped grants and pass the resource along with the check:

A resource is just an object: \{owner, sharedWith\} — owner is the owning userId and sharedWith is a list of userIds. Your app knows who owns what, so the engine never needs a resource registry. A can() call with a resource succeeds if any applicable dimension grants: the plain permission, "own."+perm (when owner is the user), or "share."+perm (when the user is in sharedWith). Grant own.doc.* to your baseline role and share.doc.edit to editors — no per-document ACL bookkeeping.

Server enforcement (authoritative)

Paste rbac("serverScript") into a <script type="text/x-server-plugin"> block, set the two RBAC_ADMIN_* constants at its top, then gate your own RPC handlers with rbacRequire(conn, "perm") — passing \{resource: \{owner, sharedWith\}\} when the action targets a document. Because the script is public source, only the SHA-256 hash of your admin password lives in it:

generating…

Generate a hash in any browser: await crypto.subtle.digest("SHA-256", new TextEncoder().encode("your-password")).then(b => Array.from(new Uint8Array(b)).map(x => x.toString(16).padStart(2,"0")).join("")) — paste the hex string as RBAC_ADMIN_PASSWORD_SHA256.

How it works

Permissions are dot-separated strings — doc.edit, admin.users.ban — and roles grant patterns. Matching walks both strings segment by segment:

patterngrants
*everything
doc.*doc, doc.read, doc.a.b, …
doc.editexactly doc.edit — never a sibling or a deeper permission
doc.edit.*doc.edit and anything below it

A pattern never grants outside its own branch, and an exact pattern never grants deeper or sibling permissions.

Grants, denies and the deny-overrides rule

A role is { perms, denies, inherits }. A request for permission p is allowed iff the user's whole role set (direct + every inherited role, transitively) contains a grant that matches p and contains no deny that matches p. Deny-overrides is order-independent — a deny reached through an inherited role or a sibling role always beats a grant anywhere in the set, so a grant can never shadow a deny.

Role inheritance

Roles inherit other roles transitively. rolesOf(user) returns the full closure, hasRole sees inherited roles, and effectivePermissions is the union of every granted pattern. Cycles (A inherits B inherits A) are handled with a visited set, so a self- or mutually-referential graph can never hang a check.

Bans

A banned user is denied everything — a ban overrides even a * grant — and is enforced at every boundary:

  1. the permission layer — can() returns false;
  2. login — your handler should reject them (the demo does: "account banned");
  3. live sessions — banUser revokes them via rbacKickUser, unbinding and closing each bound connection with code 4001, reason "banned".

Resource scoping

A resource is { owner, sharedWith }. can(user, perm, resource) runs up to three deny-aware checks and allows if any passes: the plain permission (global grant), "own." + perm (only when resource.owner === user), and "share." + perm (only when resource.sharedWith includes the user). Each dimension is a full grant+deny check. So grant own.doc.* to a baseline role ("members manage their own docs") and share.doc.edit to editors, and ownership/sharing work with no per-document ACL bookkeeping.

The server layer

The authoritative server runs inside a server-plugin socket. At boot it rebuilds its in-memory model from a versioned binary layout stored in the durable state Uint8Array — roles, user→role assignments, bans, and a ring of the last 200 audit entries. Corrupt or unknown-version state is discarded and rebuilt deny-by-default rather than crashing. Key mechanics:

  • Identity binding — rbacBindIdentity(conn, userId) is called only from your own authenticated login handler (it is deliberately not an RPC). rbacAllow / rbacRequire gate your handlers, optionally with {resource} for scoped checks.
  • Admin gate — a connection is admin if it is bound to a userId in RBAC_ADMIN_USERS, or if it completed the rate-limited (10/min/IP) password handshake against RBAC_ADMIN_PASSWORD_SHA256. The script is public source, so only the SHA-256 hash of the admin password may live in it.
  • Mutations — every admin mutation bumps a revision counter, persists to state, notifies subscribers on the rbac:changed pubsub channel, and is written to the audit ring.
  • Bans are live — banUser kicks the user's current sessions on the spot (see Bans above).

Make it yours

  • Import. Add the line from the Import section to the top of your main.pjs — the name on the left is how you call it.
  • UI gating. rbac("engine") for client-side, offline role logic — show/hide controls by engine.can(userId, "doc.edit").
  • Real security. rbac("serverScript") into a <script type="text/x-server-plugin">, set RBAC_ADMIN_USERS / RBAC_ADMIN_PASSWORD_SHA256, then rbacRequire(conn, "perm") inside every handler that mutates data.
  • Login. Never expose rbacBindIdentity as an RPC — call it from your own authenticated login handler after verifying credentials.
  • Stay robust. Bad input to $output returns a readable (rbac: …) placeholder — it never throws.
  • Publish. Save this generator, then import it from anywhere using the standard import syntax.

Notes

  • Client-side checks are cosmetic — the server is the gate. Deny-by-default: a user with no roles is allowed nothing.
  • The server script is public source; only the SHA-256 hash of your admin password should ever live in it. Rate-limited password handshake included.
  • Permissions are dot-separated strings (doc.edit, admin.users.ban) matched by wildcard patterns.
  • Resources scope permissions: engine.can(user, perm, \{owner, sharedWith\}) and rbacRequire(conn, perm, \{resource\}) add the own./share. dimensions — no per-document ACL bookkeeping.
  • Every admin mutation is written to a durable audit log (last 200 entries, survives restarts) — read it with client.adminAudit().
  • Ban lifecycle: a banned user is denied at the permission layer (rbacDb.can returns false), rejected at login, and — if they're online — their session is revoked immediately by rbac.banUser (socket closed with code 4001, reason "banned").
  • Every $output argument is read through .evaluateItem, so plain values and Perchance lists work alike.
