🪄 smb-integration

The Small-Business Generator Pipeline framework — a suite of Perchance tools (idea-incubator → project-master → the-ledger) linked through a shared file-based bus. Built on Rathji's plugin template structure. This page is the full usage reference for the framework.

What this is

A Perchance plugin is just a normal generator written to be reused. The one special thing is the $output function at the bottom of main.pjs — when another generator imports this one, the name on the left of the import line becomes that function. The lists, data and helpers below it are all ordinary Perchance code.

This generator is the pipeline's shared framework: the bundle envelope & bus protocol, the pipeline manifest, and the connector toolkit every tool imports. This page doubles as docs and a live test harness — every claim below is exercised here.

How the pipeline works

Five moving parts — and every one of them is optional except the file bus itself:

  • The file bus — every bundle is a JSON text file under its tool's own namespace (https://editable.uploads.dev/file/<toolStub>/<bundleName>). Files are the canonical, cross-device storage: they survive reloads, work with every tool closed, and never depend on a server being online.
  • The manifest — one shared bundle (smb-integration/manifest) says which tool publishes/consumes what, the active bundle file names, and schema versions. Tools discover each other from it; a new tool joins by registering, not by rewiring the others.
  • Workspace stores — each tool keeps its canonical data in one versioned JSON file of its own (e.g. project-master/workspace), with a local kv cache for instant reads, monotonic timestamps so same-millisecond edits never collide, and conflict detection when two devices edit the same file.
  • The connector — the one import every tool adds. It handles edit keys (the wallet), idempotent publishes, typed pulls, freshness tracking, and optionally reporting to the hub.
  • The hub — an optional live layer: a small server-plugin generator holding only a latest-per-key index (never the payloads), so subscribed tools learn of upstream updates within seconds and can render a data-age dashboard — with automatic fallback to the file bus when it's unreachable.

A typical flow: idea-incubator exports an idea bundle → project-master adopts it, runs milestones, and publishes project / milestone-event bundles → the-ledger ingests the billing events into invoice drafts, posts them with double-entry integrity, and replies with payment-receipt bundles → project-master and idea-incubator pull those receipts and render paid / in-progress / adopted status. Every hop is a file write plus a file read.

Bundle envelope

Every tool publishes and consumes the same JSON envelope, so consumers identify provenance and freshness without guessing. Canonical fields: schemaVersion (envelope format version), bundleType, tool (publishing generator's stub), toolDisplayName, exportedAt (ISO timestamp), source (workspace file/records exported from), and payload.

Self-tests exercise smbBuildEnvelope() / smbValidateEnvelope() — valid builds, JSON round-trips, every missing/malformed field, unknown bundle types, schema-version gaps, and garbage inputs.

Bundle-type schemas

Each bundle type has a versioned payload schema, independent of the envelope version. Every payload declares its own schemaVersion; validation checks required fields, types, per-type rules, and flags schema-version gaps. Required fields per type, pulled live from the registry:

Pipeline registry & manifest

One shared pipeline-manifest bundle is the single source of truth: it lists every tool — stub, display name, what it publishes, what it consumes, and current schema versions (auto-derived from the schema registry). Tools discover each other from it; a new tool joins by registering itself, not by rewiring the others. The manifest lives at https://editable.uploads.dev/file/smb-integration/manifest (published for real by the bus adapter).

Register a new tool adds a "time-tracker" to the live demo manifest (an unknown timesheet type, so it also demonstrates the schema warning).

Bus write adapter

Every tool publishes bundles as text files under its own namespace: https://editable.uploads.dev/file/<toolStub>/<bundleName>. The first publish creates the file and returns an edit key (kept in the tool's local store); later publishes update the same file with that key and report the new edit count for cache-busting. Bundles over 5 MiB are rejected before any network call; quota / rate-limit / unsaved-generator failures come back as readable typed errors, never thrown.

Dry-run validates, serializes and size-checks without touching the network. Publish for real needs this generator saved (unsaved generators can't write to the bus); a second publish to the same name within ~10s is superseded — the readable rate-limit error that proves the failure surfacing. It publishes to <current generator>/bus-demo, so it never touches the real manifest.

Bus read adapter

Any tool can pull an upstream bundle by its public URL. The adapter fetches, parses, and schema-validates it, then compares its exportedAt against what the reader already has and returns a clear typed result: fresh (newer than your copy, or no copy yet), unchanged (same timestamp), older (upstream is older than your copy — the gap is named), or a specific failure — 404, network, malformed, or a named schema gap (vN vs this library's vM). Never throws.

The default URL is a real bundle published on the bus by the write adapter. Pull once → fresh; pull again "as reader" → unchanged. Change the file segment to a bogus name to see a typed 404.

Connector module

One drop-in client any future tool imports. A tool creates its connector, configures it with the manifest URL, and gets the whole bus behind four methods — configure(manifestUrl), publish(bundleType, payload), listUpstream(bundleType), pull(bundleName) — all returning the same typed results as the adapters. New business tools get bus access without reimplementing the protocol.

Publish the pipeline manifest writes the real shared manifest to <current generator>/manifest (needs this generator saved). Discover upstream loads it and lists who publishes each bundle type. Publish via connector publishes an idea bundle; Pull via connector pulls it back through the same API a consumer tool uses.

Edit-key wallet

Every tool's editable-file edit keys live in a per-device wallet, so a tool never asks the bus "create me a file" when it already owns one. smbWallet() is the framework's default (localStorage-backed); smbCreateWallet() builds one with an injectable store. smbPublishBundle() auto-notes the edit key on every successful publish, and the wallet records first-seen / edit counts per file. Persisted layout: smb:editkey:<tool>:<name> (the flat key — source of truth), smb:wallet:tool:<tool> (JSON index), smb:wallet:meta (device id). Status per tool: ok (all expected keys held), clean (nothing expected yet), empty / partial (a key is expected but missing — possible loss), and recovered.

When keys go missing (new device, cleared storage) the manifest can still say what a tool should own. Detect loss checks each expected file upstream: a file that exists on the bus with no local key is confirmed lost. Recovery publishes nothing — it just adopts a fresh bundle namespace (e.g. idea-<deviceToken>-<time>-<rand>) for each published type, and re-registers that tool in the manifest with activeNames so upstream discovery follows the fresh files while the old ones stay readable at their public URLs. Everything here is local + reversible.

Refresh status shows what this device's wallet holds for each tool (from the default manifest; this generator's tool stub is smb-integration). Detect loss checks the bus for each expected-but-unkeyed file (a 404 → never published, nothing lost). Recovery plan proposes a fresh namespace (stored on window._smbRecoveryPlan); Apply adopts it locally — a real recovery would then re-register the tool in the manifest with activeNames; Undo reverses it.

Freshness & sync-status

Every tool tracks, per bundle, the last time it pulled that bundle, the last time it published it, and (for files it writes) its upstream edit count. smbSyncTracker() persists one JSON record per (tool, bundle) under smb:sync:<tool>:<bundle>; smbPublishBundle() and connector.pull() auto-note every success, so the tracking is automatic and can never break the bus. A status() call renders the "last synced X ago" line per bundle and flags a bundle stale when its last successful sync is older than a configurable threshold (default smbSyncStaleAfterMs = 1 hour; overridable per call and per tracker). Consumed bundles also report the data age of the upstream file (from its exportedAt) — the read path exposes no server edit count, so that's the honest freshness signal until the hub (§33–35) supplies true cross-device counts.

Refresh sync status shows this tool's (current generator's) sync records with their "last synced X ago" lines and stale flags (threshold from the input — set it low to watch a fresh record go stale). Record a publish notes a publish of idea (edit count from this device's ledger); Record a pull notes a pull of project from project-master (upstream data exported 2h ago → its data age shows); Simulate stale records that pull as if it happened 2 minutes ago — over a 30s threshold it is flagged stale. Clear records wipes this tool's records so the demo repeats.

Conflict preview & safety nets

Two devices editing the same workspace on the shared bus eventually disagree. The framework detects the both-changed conflict instead of silently overwriting, and gives you a field-level preview table (smbConflictPreviewHtml) plus a typed resolver (resolveConflict("mine"|"theirs"|"merge")). And so no edit is ever lost for good, every store can download a full backup (smbBackupDownload) and restore it again later (smbRestoreFromFile).

Show conflict preview renders the field-level table (red = truly conflicting fields, grey = unchanged). The resolve buttons run the raw resolver on the same local/remote snapshot to show what each mode keeps. Run self-tests simulates two devices diverging on one shared bus file, detects the conflict, resolves it three ways, and checks the flat-payload resolver.

Download a workspace backup builds a demo the-ledger workspace store, writes a couple of records, and downloads its full backup JSON. Pick that (or any smbRestoreFromFile backup) in Restore from file to parse it and apply it to a fresh store — the canonical file is safe on the bus even when the local cache is wiped.

Live pipeline hub

The hub is an optional live index + pub/sub relay for the file bus: tools report "I just published bundle X (edit N)" and subscribed peers hear about it in seconds — no polling, no edit-key handshakes on the read path. It has two transports that expose the same client surface:

  • Socket mode — a direct server socket to a hub page that embeds the server script (this page ships one). smbHubIndex(\{ createSocket \}).
  • Bridge mode — any tool embeds the hub page in a hidden iframe and exchanges subscribe/notify/report/query JSON over postMessage, no server-plugin import needed. smbHubIndex(\{ hubUrl \}). When the hub is unreachable the bridge degrades to polling the file bus directly, so the pipeline never depends on the hub being open.

Runs against this generator's own emulated hub server (the text/x-server-plugin script above) — while unsaved it's the local emulator; after save it talks to the real server-plugin. Report a publish broadcasts a change event that any subscribed client (open a second tab!) receives live. Run self-tests proves the client protocol + registry + fan-out against a hermetic fake socket.

Full round-trip drives the real message router (the exact code the hub page runs) over the mock transport: bridge → router → server → change event → glue → registry → notify → bridge. Hub down → degrade points the bridge at a router that never answers, watches it fall back to hub_unavailable, then shows the poll() fallback picking up a fresh upstream bundle straight off the bus.

Data-age dashboard

Every tool can render a pipeline status panel (smbPipelineStatusPanel): for each bundle the tool consumes it shows the upstream publisher, the upstream's last-published time and edit count (from the hub index when reachable), the data age, and the tool's local sync line. One-click per-row and per-panel refresh re-pull from the bus. When the hub is offline the panel falls back to the local sync tracker, so it always has an answer.

Shown for the-ledger (consumes milestone-event from project-master). Hub live connects the socket client and fills "upstream last published" from this page's emulated hub; hub offline renders the same panel with only local sync timestamps. Refresh inside the panel re-pulls each row.

Make it yours

  • Describe. Update the $meta title, description and tags.
  • Write the logic. Add helpers in section 3 and call them from $output. It should return a string (usually HTML) or a Promise.
  • Trim. Delete section 1 (embedded data) and the smbIntegrationDefaults() helper if you don't need a payload.
  • Stay robust. Never throw — return a readable (...) placeholder on bad input, like the skeleton's $output does.
  • Publish. Save this generator, then import it from anywhere using the standard import syntax — see the Import section above.
