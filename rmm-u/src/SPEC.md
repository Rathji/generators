```markdown
You are building an RMM (Remote Monitoring and Management) platform for Perchance, called rmm-u — a single integrated application that installs a lightweight agent on every managed endpoint, watches each machine's health continuously, raises alerts on problems, and lets a technician remotely act on the machine. It is modeled on the breadth of Datto RMM and ConnectWise RMM (Automate/Asio): a multi-tenant console; a device inventory/CMDB; a downloadable, per-provider agent that enrolls a machine, heartbeats, collects system/hardware/software/patch/security/backup data and performance metrics, executes queued commands and scripts, installs patches and software, and self-updates; a monitoring and policy engine (device groups, policies, monitors, thresholds, schedules, maintenance windows); an alerting and response pipeline; an automation engine; patch and software deployment management; security/compliance and backup-verification monitoring; reporting and dashboards; and two-way integration with the pipeline's PSA (psa-u) and documentation tools. Two things make this different from a browser-only app and must be handled honestly. First, the agent is a real program for a real, non-browser endpoint (a PowerShell script for Windows and a shell script for macOS/Linux), generated as a per-provider installer carrying the collector address and a one-time enrollment token. Second, the collector is the optional server-plugin hub. Because the collector script runs on a shared server and its source is public, the design must never place a static secret in it: each device receives its own high-entropy enrollment token at install time, the collector stores only that token's hash, every check-in and job result is authenticated per device, and a revoked device is refused on reconnect. Focus entirely on delivering robust, modular, and testable features based on the functional requirements provided.

### Core Framework Tasks for `.pjs`

#### Phase 1: [Foundation — Tenancy, Console & Data Model]
1. [x] [App shell & navigation]: Provide the console frame with navigation across every station (Dashboard, Devices, Groups, Policies, Monitors, Alerts, Automations, Patches, Software, Security, Reports, Integrations, Admin), with consistent empty/loading/error states and layouts that work at phone and desktop widths.
2. [x] [Tenancy & data storage]: Model each managed-service provider as a versioned JSON document in rmm-u's own storage namespace containing its sites, device groups, devices, policies, monitor definitions, alert history, script library, patch/software state, and automation rules — with a locally cached edit key and a fast local cache so the console survives across devices and reloads.
3. [x] [Device hierarchy & inventory record]: Implement the provider → site(s) → device-group → device hierarchy and a rich device record (hostname, display name, OS and version, architecture, manufacturer/model, serial, domain/workgroup, CPU, RAM, disks, IP/MAC, logged-in users, tags, warranty/support dates, agent version and last-seen, linked configuration record in the documentation tool) that is the anchor every other feature attaches to.
4. [x] [Master configuration]: Provide the system-wide configuration the rest of the platform depends on — monitor types, severity levels, notification channels, schedules and business-hours calendars, maintenance-window definitions, patch classifications, software categories, tag/group taxonomies, and script categories — editable in one admin console with change history.
5. [x] [Sync, conflict, backup & versioning]: Reconcile every document against its canonical copy on startup, offer keep-mine / keep-theirs / field-level-merge on a two-console edit before overwriting, provide one-click full backup (download plus a published backup document) with validated restore, keep a version history with restore, and report per-document size against the storage ceiling with guided archival.

#### Phase 2: [The Agent — Install, Enroll, Report, Act]
6. [x] [Agent packaging & installer generator]: Generate a per-provider installer — a Windows PowerShell script and a macOS/Linux shell script — that embeds the collector address, the provider identity, the assigned site/group, and a one-time enrollment token, and that installs the agent (scheduled task/systemd/launchd service), registers it to start on boot, and prints a clear success/failure status with the device's initial ID.
7. [x] [Enrollment & device identity]: Implement the enroll handshake — the one-time token is exchanged for a durable per-device credential, the collector stores only the hash of that credential and never the plaintext, the installer token is single-use, re-enrollment/credential rotation is supported for a legitimate reinstall, and a revoked device is refused on reconnect.
8. [x] [Heartbeat, presence & capabilities]: Implement heartbeat with a configurable interval, device liveness/offline/stale detection on the collector side, clock-skew and network-change reporting, agent-version reporting, and a capabilities report (which collectors, commands, and features this agent supports) so the console can adapt per device.
9. [x] [System inventory collection]: Collect and send hardware inventory, OS details, installed software, services, patches, disks/volumes, network interfaces, local users and groups, security/AV status, and backup status — as deltas against the last known state rather than full resends, so the collector and console stay current without flooding the channel.
10. [x] [Performance metrics collection]: Collect CPU, memory, disk space and I/O, network throughput/latency, uptime, and any custom performance counters on a configurable sampling interval, aggregate locally, and send summarized samples with configurable retention so metric volume is bounded by design.
11. [x] [Command & script execution]: Implement the job path — the collector queues a job for a device, the agent fetches it on its next check-in, executes the supplied PowerShell/bash/cmd script with parameters, timeout, and working directory, captures exit code plus stdout/stderr, and returns an authenticated result — with per-OS command compatibility and a clear failure result when a job is unsupported on that OS.
12. [x] [Agent resilience, self-update & safety]: Buffer results offline and resume on reconnect, retry with exponential backoff and jitter to avoid reconnect storms, verify the collector's TLS/identity, support self-update with rollback to the prior version, enforce resource caps so the agent never materially impacts the endpoint, and provide clean uninstall/self-remove.
13. [x] [Agent diagnostics & support]: Provide a local rotating log, an agent self-test (can it reach the collector, is it enrolled and heartbeating), a console action to pull the agent's recent logs, and documented troubleshooting for the case where an installed agent cannot reach the collector.

#### Phase 3: [Collector & Realtime Backend]
14. [x] [Collector service]: Build the collector as the optional server-plugin hub — authenticating each device's check-in against its stored credential hash, accepting inventory/metric/job-result payloads into durable state, tracking last-seen, and returning any queued jobs and configuration in the same response.
15. [x] [Job queue & dispatch]: Implement the job queue — jobs enqueued from the console for one device or many, delivered to each agent on its next check-in, with per-job state (queued/delivered/running/succeeded/failed/timed-out), retry and expiry policy, and result correlation back to the originating console action or automation.
16. [x] [Event stream & degraded mode]: Broadcast device state changes, new alerts, and job results to open console sessions in realtime, and degrade gracefully to polling refresh when the realtime connection is unavailable — including clear UI that tells the user which mode it is in.
17. [x] [Retention, batching & scale]: Define and enforce retention (raw metrics window, roll-ups to hourly/daily, job and log retention, alert history), batch and compress payloads, and bound per-device rate and connection counts so one misbehaving or compromised device cannot exhaust the collector.

#### Phase 4: [Policies, Monitoring & Automation]
18. [x] [Device groups & tags]: Support static groups and rule-based dynamic groups (by OS, tag, site, installed software, or attribute), with tags as the primary way to target policies and automate actions.
19. [x] [Policy engine]: Make a policy a named collection of monitoring, patch, software, and automation settings applied to one or more groups, support multiple policies with a defined inheritance/precedence order, and provide an effective-policy preview showing exactly what a given device will receive and from which policy each setting came.
20. [x] [Monitor types]: Implement the monitor catalogue — up/down, CPU/memory/disk threshold, service/process state, Windows event log (by source/EventID/level), application/port/web check, custom script monitor returning a status/value, SNMP/network-device monitor, agent-offline/stale, and patch/AV/backup monitors — each with thresholds, a "for N minutes" duration before firing, severity, and per-device or per-group overrides.
21. [x] [Schedules & maintenance windows]: Support schedules (business hours, after-hours, weekends, per-client timezone) and maintenance/blackout windows that suppress alerts and defer non-essential jobs while still recording what was suppressed for audit.
22. [x] [Automation engine]: Implement trigger → condition → action automation (triggers: alert fired/cleared, monitor state change, device online/offline, schedule, manual, or inbound webhook; actions: run script/component, restart a service, deploy a patch or package, send a notification, create or update a ticket in psa-u, call a webhook), with dry-run/preview, approval gating for destructive actions, and a full run history and audit trail.
23. [x] [Script & component library]: Provide a reusable library of scripts/components with typed parameters, per-OS variants, versioning, category tags, and an import/export format, and validate parameters before execution so a library script cannot be used to run unsafe input on an endpoint.

#### Phase 5: [Alerting & Response]
24. [x] [Alert lifecycle]: Implement the alert record and its lifecycle (fired → acknowledged → resolved/auto-cleared), with de-duplication and flapping suppression, snooze, severity mapping, root device/site/group context, and a link to the monitor and policy that produced it.
25. [x] [Notification routing & escalation]: Route notifications by severity and site to email/in-app/webhook with escalation paths (unacknowledged alert escalates after N minutes, on-call rotation), per-recipient quiet hours and digests, and strict de-duplication so a flapping device cannot spam a recipient.
26. [x] [PSA ticket integration]: Turn alerts into tickets and back — create a psa-u ticket on alert (with de-duplication so a recurring alert updates the existing ticket instead of opening a new one), link the ticket to the device and its configuration record, update the ticket as the alert changes, auto-resolve the ticket when the alert clears, and reflect ticket status back on the alert.
27. [x] [Alert triage workspace]: Provide a prioritized triage queue with grouping by device/site/monitor, bulk acknowledge/assign/resolve, and metrics such as alert volume, mean time to acknowledge, and mean time to resolve.

#### Phase 6: [Patch Management]
28. [x] [Patch policy]: Configure patch policy per OS and patch classification (approve/deny/defer with deadlines, maintenance-window installation, reboot behavior and reboot-window, deadline enforcement) with a clearly stated default and per-group overrides.
29. [x] [Patch scanning & compliance]: Scan devices via the agent for missing patches, track per-device compliance against the applicable policy, age missing patches (how long a device has been non-compliant), and expose it per device, group, site, and provider.
30. [x] [Patch deployment & audit]: Deploy approved patches as agent jobs, handle failures with retry and reporting, schedule and track required reboots, capture before/after compliance, and produce an auditable patch-compliance report per client.

#### Phase 7: [Software Deployment & Inventory]
31. [x] [Software catalog & deployment packages]: Maintain a catalog of deployable software with silent install/uninstall/update command templates, per-OS variants, detection rules (so already-installed devices are skipped), parameters, source location, and checksum.
32. [x] [Software deployment & detection]: Assign packages to devices or groups, report installed / not-installed / pending / failed per device, target specific versions, support downgrade/rollback where the package defines it, and log every deployment action to the device's audit trail.
33. [x] [License & inventory reconciliation]: Reconcile installed software against owned licences per client, flag expired, over-deployed, or unsanctioned software, and export an inventory/licence report per client.

#### Phase 8: [Security, Compliance & Backup Monitoring]
34. [x] [Security posture monitoring]: Monitor and report endpoint security state — AV/EDR present and up to date, firewall enabled, disk encryption (BitLocker/FileVault) state, OS patch currency, local admin/account changes, and other configurable baseline items — per device and per client.
35. [x] [Compliance baselines & drift]: Define compliance baselines as a policy, detect drift from the baseline, report non-compliant devices with the exact failing checks, and offer remediation through the automation engine.
36. [x] [Backup verification monitoring]: Ingest backup job status from common backup products, track last-successful-backup and missed-backup per device, escalate backup failures through the alert pipeline, and prompt periodic recovery-test confirmation with an auditable record.

#### Phase 9: [Remote Access & Field Actions]
37. [x] [Remote shell/console]: Provide a browser-based remote terminal that runs commands through the collector → agent path, with session logging (who ran what, when, on which device), permission gating, a confirmation step and deny-list for dangerous commands, and clear no-output/timeout handling.

43. [x] [Data-quality linter]: Audit for the rot a real RMM accumulates — agents offline or stale beyond a threshold, devices with no policy, monitors with no notification route, duplicate device records, devices missing a site/owner, orphaned groups, alerts that can never auto-clear, and scripts with unsafe parameters — and report each with the offending record.

49. [x] [Realtime console]: Stream live device state, alerts, and job progress to all connected console sessions so multiple technicians see the same reality within seconds, with presence ("who else is on this device") and a graceful fallback to polling.
50. [x] [Multi-user audit & rate control]: Authenticate console users to the hub with their role, rate-limit and group connections against abuse, log every remote action to the true actor's audit trail, and ensure a change made by one user is never silently overwritten by another.
```
